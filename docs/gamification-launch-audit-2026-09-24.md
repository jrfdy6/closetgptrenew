# Gamification launch coverage audit — 2026-09-24

This is an independent cross-boundary audit of source **cfe6cdd425e93eee624d3ac7c9b4c4e3236aa8b3**, on `codex/gamification-launch-polish`. Implementation owners are changing the shared checkout concurrently. The matrix below records the frozen baseline and required acceptance coverage; it is **not** a claim that subsequent fixes have passed. No production data, provider, Stripe, or cloud mutation was used. Local source reads and pure/in-memory probes establish these findings.

## Launch conclusion

Canonical outfit wear is the only fully connected reward action from a mounted user action to a durable reward receipt and a visible XP/level notification. Rating commits feedback and normally awards XP, but drops the notification/refresh path; upload/onboarding do not call their reward milestone handlers. The catalog advertises **59 definitions**, **36 initially available**. The weekly worker rewrites `featured` to one of three IDs, reducing availability to **16–17** (16 always-available plus, sometimes, one rotating weekly challenge). Eleven of the 16 always-available definitions lack a correct end-to-end completion path at this baseline.

A catalog entry, a helper method, and a passing generic projection test are three different kinds of evidence. Each offered challenge needs a real action-to-receipt-to-visible-completion test. Dormant gacha/role helpers and unmounted UI components must not be advertised as completed launch features.

## Actionable findings

1. **P1 — Offered challenges cannot finish.** `wear_projection.py:88–90` explicitly excludes feedback/pull/role/token/level/badge/upload rules as “processed by their own action,” but those action progressors are absent. `complete_catalog` instead counts wear categories despite promising uploads. The normal upload path never invokes the separate cold-start checker. A checker call updates progress and gives at most one missed milestone per call, never completes the quest or grants its advertised token reward (`challenge_service.py:303–389`).
2. **P1 — Hidden Gem Hunter cannot start, and a shallow fix could grant it for new uploads.** `challenge_service.py:43` calls `.get` on `ForgottenGemsResponse` then swallows the exception. After fixing the response type, eligibility must exclude unknown/null last-worn dates: the discovery endpoint intentionally lists never-worn items, and the selected-item shortcut in `wear_projection.py:85–87` bypasses the 60-day rule. Test genuinely dormant vs newly uploaded pieces.
3. **P1 — Seasonal/theme data never reaches the rule.** `wear_projection.py:119–122` requires event `season`/`theme`, but `outfit_wear.py:234–245` omits them; allowed history metadata is only occasion/mood/weather/notes/tags (`:270`). Seasonal and holiday challenges stay at zero through supported wear paths.
4. **P1 — Completion and reward feedback is missing despite committed results.** Completed tab is a placeholder (`ChallengeList.tsx:160–165`); useChallenges fetches only active/available. Actual rating discards its reward response and never emits its subscribed event. Dashboard upload callback refreshes dashboard counts only (`dashboard/page.tsx:903–908`). Tests that manually dispatch events do not prove the producer exists.
5. **P1/P2 — Recurring cadence and activation semantics contradict copy.** Only weekly starts receive a period instance ID and expiry (`challenge_service.py:99–113`). Daily/monthly/quarterly definitions become permanent instances. Completed always/nonweekly entries reappear as available but restarting returns the old completed record. Flash Challenge stops accepting progress after 24 hours but remains active until its seven-day expiry. “Create” color/pattern/context goals only count wear; lifetime/first-N goals count events after joining. Formality Range counts distinct occasion strings rather than formality levels. Decide and test truthful copy and boundaries without changing reward formulas silently.
6. **P1 — Rating can acknowledge success while permanently losing its 5 XP.** Feedback commit and XP award are separate; XP exceptions are swallowed and no reward outbox is queued (`routes/outfits/routes.py:701–723`). A later user retry can settle it, but the UI reports success and does not retry, while daily maintenance repairs only its separate seven-day bonus. Fault-inject between commits and require eventual one-time settlement.
7. **P2 — Dormant gacha/role promises exceed delivered behavior.** No user action reaches gacha/role APIs. Rare and legendary rewards contain generic text rather than the promised generated technique/template; common pulls replace `pending_xp_bonus=50` rather than accumulating distinct paid pulls (`addiction_service.py:317–335`). Role perks have unconsumed fields; promotion count includes undone history. Keep dormant behavior out of launch claims until verified.
8. **P2 — Baseline badge/streak/annual edge cases lack boundary coverage.** Badge checks query only `userId` and count deleted/conflicting rows; some catalog/cycle badges lack enum metadata. Stored streak can remain current after days without engagement. Annual `_ms` treats numeric signup seconds as milliseconds (`wear_projection.py:58–63,327`), shifting legacy account cycles. Existing annual tests cover backdated projection, not legacy signup formats.
9. **P2 — Failure and concurrency UI gaps.** TVE errors suggest onboarding, AI-fit errors suggest rating, and badge errors disappear rather than distinguishing unavailable data. Challenge start has an unused pending state and remains clickable. Scope confirmation: unmounted LevelUpModal, BadgeUnlockModal, ThirtyWearsProgress, GWS/CPW/Utilization/Audit cards are not current visible failures; do not count their copy as shipped feature proof.
